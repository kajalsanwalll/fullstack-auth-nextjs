Notesphere

01 — Overview

What is Notesphere?

Notesphere is a full-stack note-taking application where users can create rich notes with text and images, pin important ones, toggle visibility between private and public, and download notes as PDFs. Public notes go through an admin moderation queue before appearing publicly, preventing spam and abuse.

The app uses a unified Next.js codebase — both the React frontend and the REST API live in the same repo using Next.js App Router API routes, eliminating the need for a separate backend server.

02 — Architecture

Tech stack breakdown

Frontend
Next.js 14 + React

App Router, client components, file-based routing. axios for HTTP, react-hot-toast for notifications.

API Layer
Next.js Route Handlers

REST endpoints under /api/users/ and /api/admin/. Same process as the frontend — no separate Express server.

Database
MongoDB + Mongoose

Document model fits notes (variable fields, embedded images array). Mongoose for schema validation and querying.

Auth
JWT + HTTP-only Cookies

Stateless auth. Tokens stored in HTTP-only cookies — not localStorage — to prevent XSS token theft.

File Storage
Cloudinary

Images uploaded via /api/users/upload, stored on Cloudinary CDN. URLs saved in the note document.

Export
html2pdf.js

Client-side PDF generation from note HTML. No server involvement — runs entirely in the browser.

Questions you'll be asked

01 DesignWalk me through the architecture of your application. ▶
model answer

Notesphere is a full-stack app built on Next.js 14 using the App Router. The frontend is React with client-side state — no SSR for authenticated pages since data is user-specific. The backend is a set of Next.js Route Handlers that serve as REST endpoints, connected to MongoDB via Mongoose for persistence and Cloudinary for image storage.

Auth uses stateless JWTs stored in HTTP-only cookies. The app has two user roles: regular users who create and manage their own notes, and admins who moderate notes before they go public. Everything is deployed as one Next.js project — no separate backend service.

02 SecurityWhy HTTP-only cookies for JWT instead of localStorage? ▶
model answer

localStorage is vulnerable to XSS. Any injected JavaScript can read localStorage.getItem('token') and exfiltrate the JWT. HTTP-only cookies cannot be read by JavaScript at all — they're only sent by the browser on matching requests.

  • HTTP-only — inaccessible via document.cookie, blocks XSS token theft
  • Secure flag — only sent over HTTPS in production
  • SameSite=Strict — mitigates CSRF by blocking cross-site cookie sending

The trade-off is that cookies are automatically sent on every request (even ones that don't need auth), and you need to handle CSRF more carefully. But for a web app with a same-origin API, this is the correct choice.

03 ScalabilityHow would this handle 1 million users? Where are the bottlenecks? ▶
model answer

Current bottlenecks and how I'd address them:

  • Database: MongoDB Atlas auto-scales reads with replica sets. For 1M users I'd add indexes on notes.user, notes.isPublic, and notes.isPinned. The public notes feed would need pagination (cursor-based, not offset) to avoid full collection scans.
  • Image uploads: Currently synchronous — user waits for Cloudinary. At scale I'd move uploads to a background job queue (e.g. BullMQ + Redis) and return a presigned URL for direct browser-to-Cloudinary upload, removing the API server from the upload path entirely.
  • API layer: Next.js serverless functions scale horizontally on Vercel/AWS. But JWT verification on every request adds CPU cost — I'd add Redis-based token caching or switch to a dedicated auth service.
  • PDF export: Currently client-side (no server cost). This is actually a good scalability decision — it doesn't scale with users at all since it runs on their device.
04 Trade-offsWhy MongoDB over PostgreSQL for this use case? ▶
model answer

Notes are a good fit for documents because the schema is variable — a note might have 0 images, 5 images, or just text. In SQL, images would be a separate note_images table requiring a JOIN on every note fetch. In MongoDB, images are an embedded array — one read, no join.

However, I'd acknowledge trade-offs: if I needed complex queries like "all public notes by users who signed up in the last 30 days with more than 10 notes", MongoDB's aggregation pipeline is verbose compared to SQL. For this app's query patterns (find by user, find by public status, search by text), MongoDB is a clean fit.

Key insight to mention: The choice isn't "MongoDB is better" — it's "MongoDB fits this data shape and these query patterns." Always frame DB decisions around access patterns, not personal preference.

05 DesignHow does the admin moderation system work? How would you prevent a malicious user from bypassing it? ▶
model answer

When a user toggles a note to public, it enters a pending state in the database. The /public-notes endpoint only returns notes where isPublic: true AND status: 'approved'. The admin endpoints /api/admin/approve-note and /api/admin/reject-note are protected by a middleware check that verifies user.isAdmin === true from the JWT payload.

Bypass vectors and mitigations:

  • Direct API call with forged token: JWT is signed with a server secret — you can't forge it without the secret
  • Privilege escalation: The isAdmin flag is set server-side only, never in a user-controlled field
  • Race condition: The approval is a single atomic MongoDB write with a status check — no TOCTOU window
  • Improvement I'd add: Rate limiting on note creation to prevent spam flooding the moderation queue
06 PerformanceThe public notes page fetches all public notes at once. How would you fix this? ▶
model answer

Yes, this is a real issue. Currently /api/users/public-notes returns the entire collection. With thousands of public notes this is slow and sends way more data than the browser needs.

I'd implement cursor-based pagination:

  • API accepts ?cursor=lastNoteId&limit=20
  • Query: Note.find({ isPublic: true, _id: { $gt: cursor } }).limit(20)
  • Response includes nextCursor for the next page
  • Frontend uses an Intersection Observer to trigger the next fetch as the user scrolls near the bottom (infinite scroll)

I'd also add a search index in MongoDB on title and content fields using MongoDB Atlas Search (built on Lucene) so the text search doesn't do a full collection scan on every keystroke — debounced server-side search instead of client-side filtering.

07 SecurityWhat are the security vulnerabilities in this app, and how would you fix them? ▶
model answer
  • No rate limiting: The login endpoint is open to brute-force attacks. Fix: add express-rate-limit or Vercel's edge rate limiting — e.g. max 5 login attempts per IP per 15 minutes.
  • Image URL injection: Notes accept user-supplied image URLs with no validation. A malicious user could point to a tracking pixel or SSRF vector. Fix: validate URLs against an allowlist of domains, or only allow uploads (not arbitrary URLs).
  • Missing CSRF protection: HTTP-only cookies prevent JS theft but not CSRF. Fix: verify the Origin header or use a CSRF token on state-changing requests.
  • No input sanitisation on note content: If note content is ever rendered as HTML (e.g. for PDF export), it could be an XSS vector. Fix: sanitise with DOMPurify before rendering.
  • Empty catch blocks: Several API routes swallow errors silently. This masks bugs and could leak server info. Fix: centralised error handler with structured logging.
08 DesignHow would you add real-time collaborative editing to notes? ▶
model answer

Collaborative editing is an operational transformation (OT) or CRDT problem. Two approaches:

  • Simple (presence + last-write-wins): WebSocket via Socket.io. Server broadcasts keystrokes, last writer wins. Fast to build, breaks with concurrent edits.
  • Proper (CRDT): Use Yjs — a production CRDT library. Each client maintains a local document, changes are merged conflict-free. Yjs + WebSocket provider gives Google Docs-like behaviour.

Infrastructure change: Next.js serverless functions don't support persistent WebSocket connections. I'd need a separate WebSocket server (Node.js + Socket.io on a long-lived instance) or use a managed service like Liveblocks or Ably.

This is a good answer because it shows awareness of the CAP theorem implication — you're trading consistency for availability in the collaborative case, and CRDTs are the principled solution.

09 PerformanceHow would you improve the Time to First Byte and Core Web Vitals? ▶
model answer
  • Currently all client-side rendered. Dashboard, public notes, and note detail pages could be Server Components — data fetched on the server before HTML is sent, eliminating the loading spinner + subsequent API call pattern.
  • Public notes page is a great candidate for generateStaticParams + ISR (Incremental Static Regeneration) — rebuild every 60 seconds. Public content doesn't change per-user.
  • Images: Use Next.js <Image> component for automatic WebP conversion, lazy loading, and size optimisation. Currently using raw <img> tags.
  • Bundle size: html2pdf.js is only needed on the note detail page — import it dynamically with await import('html2pdf.js') (already done, good) to avoid bloating the initial bundle.
  • Fonts: Add font-display: swap and preconnect to Google Fonts to reduce render-blocking.
10 Trade-offsWhy use Next.js API routes instead of a dedicated backend like Express or FastAPI? ▶
model answer

For this scale and team size (solo), co-location wins. Benefits of Next.js route handlers: one repo, one deployment, no CORS configuration, shared TypeScript types between frontend and API, zero cold-start penalty on Vercel.

The trade-offs I'd acknowledge:

  • No persistent state: Serverless functions can't hold WebSocket connections or in-memory caches between requests
  • Cold starts: Infrequently hit routes on Vercel's free tier can have 200-500ms cold starts
  • Vendor lock-in risk: Next.js route handlers have Vercel-specific behaviour (streaming, edge runtime)

If this were a team of 5+ with separate frontend and backend engineers, or if the API needed WebSockets or heavy background processing, I'd extract the backend into a dedicated Express or NestJS service with its own deployment pipeline.

11 ScalabilityHow would you implement search across notes efficiently at scale? ▶
model answer

Current implementation: client-side Array.filter() on already-fetched notes. This breaks at scale for two reasons — it fetches everything first, and it can't search notes the user hasn't loaded.

Production approach, in order of complexity:

  • Level 1 — MongoDB text index: db.notes.createIndex({ title: "text", content: "text" }). Supports full-text search server-side. Good up to ~10M notes.
  • Level 2 — MongoDB Atlas Search: Lucene-powered, supports fuzzy matching, typo tolerance, relevance scoring. Drop-in for most use cases.
  • Level 3 — Elasticsearch / OpenSearch: Dedicated search cluster for serious scale. Supports faceted search, autocomplete, synonyms, and near-real-time indexing via a change-stream consumer from MongoDB.

I'd also add debouncing on the search input (300ms) and cancel in-flight requests using AbortController to avoid result ordering issues.

12 DesignWhat would you do differently if you were starting this project again? ▶
model answer

This is a reflection question — interviewers want to see self-awareness and engineering judgment, not just feature lists.

  • Server Components first: I'd design pages as React Server Components and opt into client interactivity only where needed, rather than making everything "use client" by default. This would improve initial load performance significantly.
  • Centralised API client: Axios calls are scattered across components. I'd build a typed API client module (or use React Query / SWR) to centralise caching, error handling, and loading states — and eliminate duplicated try/catch blocks.
  • Environment-driven config: Some API behaviours are hardcoded. I'd add a proper config.ts that reads from env vars so the app is 12-factor compliant.
  • Testing from day one: No tests currently. I'd add Vitest unit tests for API route logic and Playwright E2E tests for the critical paths (create note, make public, admin approve).
